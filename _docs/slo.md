# SLO и capacity planning

## Целевые SLO (MVP)

| Метрика | Цель | Где измеряем |
|---|---|---|
| Доступность | ≥ 99.5% | `/health` извне |
| p95 latency `/api/*` (без LLM) | ≤ 300 ms | Prometheus |
| p95 latency LLM-эндпоинтов | ≤ 10 s | Prometheus |
| Error rate (5xx) | < 0.5% | Prometheus |
| Время генерации теста | ≤ 8 s | метрика AI |
| Время подборки | ≤ 12 s | метрика Matching |

## Расчёт нагрузки

Оценка на 1000 активных пользователей:

- 1000 польз × 10 запросов/день = 10 000 запросов/день.
- Среднее: ~0.12 RPS.
- **Пик:** ×20 = **~2.4 RPS**, редко до 5 RPS.

Нагрузка от LLM:

- 1000 польз × 1 тест/неделю = ~140 тестов/день.
- Каждый тест — 1 генерация + 5 оценок = ~840 LLM-вызовов/день.
- ~0.01 RPS. Плевое.

## Capacity

| Компонент | Минимум | Комфорт |
|---|---|---|
| VPS | 1 vCPU, 1 GB RAM | 2 vCPU, 2 GB RAM |
| PostgreSQL | 256 MB | 512 MB |
| Node.js heap | 192 MB | 320 MB |
| Redis | 128 MB | 256 MB |
| nginx | 5 MB | 15 MB |

**Итого:** ~1.4 GB RAM, 2 vCPU — укладывается в бюджет большинства
недорогих VPS.

## Точки роста

Что упрётся первым при росте:

1. **PostgreSQL connections.** Каждая реплика app = пул соединений.
   Решение: PgBouncer в transaction mode.
2. **LLM-latency.** Растёт линейно с нагрузкой.
   Решение: батчинг, кеш, более быстрый провайдер.
3. **Диск I/O.** PDF-генерация и резервные копии.
   Решение: вынести PDF в S3, бэкапы в объектное хранилище.
4. **Node.js event loop.** Долгие синхронные операции.
   Решение: выносить в воркеры (BullMQ).

## Мониторинг бюджета LLM

- Дневной лимит: `LLM_DAILY_BUDGET_RUB` (например, 500 ₽).
- При 80% — warning в Telegram.
- При 100% — автоматический переход в fallback (пул задач).
- Метрика `cost_per_user` — сколько в среднем тратим на одного активного.

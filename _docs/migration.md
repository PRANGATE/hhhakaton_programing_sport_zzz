# Миграция: монолит → микросервисы

Пошаговый план. Не «сделать всё сразу», а постепенно, без остановки продукта.

## Принципы

- **Strangler Fig.** Постепенно «удушаем» монолит, отрезая модули по одному.
- **Anti-corruption layer.** Прослойка между старым и новым, чтобы контракты
  не ломались.
- **Feature flag.** Переключение «внутренний вызов ↔ HTTP» одной переменной.
- **Dual-write** в переходный период: новый сервис пишет и в свою БД,
  и (временно) в старую схему монолита.
- **Никаких big-bang релизов.** Только маленькие шаги с откатом.

## Порядок выноса

1. **AI Service** — фундамент для Test, Matching, Chat.
2. **FSP Integration** — внешняя система, свой rate-limit.
3. **Test Service** — CPU-тяжёлый.
4. **Matching Service** — ML-ранжирование.
5. **Chat Service** — WebSocket-нагрузка.
6. **Notification** — фоновые задачи.
7. **Auth** — при переходе на Keycloak / ФСП ID.
8. **Analytics** — когда OLAP отделится.
9. **Moderation и ATS** — по мере готовности продукта.

## Пример: вынос Test Service

### Шаг 1. Выделить границы

- Всё, что относится к тестам (`test.*`), уже лежит в своей схеме.
- Прямых обращений к `test.*` из других схем нет.

### Шаг 2. Продублировать интерфейс

- В монолите `testService` — модуль с методами `start`, `submit`, `result`.
- Создаём HTTP-клиент с теми же сигнатурами.
- Feature flag `USE_TEST_SERVICE=http|internal` переключает реализацию.

### Шаг 3. Поднять сервис рядом

- Отдельный контейнер, тот же образ, другая entrypoint.
- Подключается к той же БД, но владеет только схемой `test`.
- Роутинг через nginx: `/api/v1/test/*` → `test:4000`.

### Шаг 4. Dual-write

- Пока переключаемся, монолит пишет и в свою таблицу, и в схему сервиса.
- Сверяем данные (job сравнения).

### Шаг 5. Отключить внутренний модуль

- `USE_TEST_SERVICE=http` в проде.
- Внутренний модуль удаляется из монолита.

### Шаг 6. Вынести БД

- `pg_dump -n test` → отдельная БД.
- Connection string в конфиге сервиса меняется.
- Никто, кроме Test Service, не ходит в эту БД.

**Время:** 3–5 дней на сервис при аккуратной работе.

## Триггеры для выноса

- >10 000 активных пользователей;
- CPU/память сервиса >70% стабильно;
- нужны независимые релизы;
- команда растёт и делится по доменам.
